# راه‌اندازی سامانه ۷۲۴ روی سرور لینوکس (VPS)

این راهنما سامانه را روی یک سرور مجازی لینوکس نصب می‌کند تا از اینترنت در دسترس باشد. همه کارها با یک اسکریپت انجام می‌شود: `deploy/install.sh`.

## آنچه نصب می‌شود

| بخش | کار |
|---|---|
| PostgreSQL | پایگاه داده، فقط روی خود سرور (از بیرون در دسترس نیست) |
| Gunicorn | اجرای برنامه Django با کاربر محدود `app724` (سرویس `724-web`) |
| Nginx | دریافت درخواست‌ها، HTTPS، سرو فایل‌های ثابت و تصاویر عمومی |
| Let's Encrypt | گواهی رایگان HTTPS با تمدید خودکار |
| ufw و fail2ban | دیوار آتش (فقط SSH و 80 و 443 باز) و مسدود کردن حمله حدس رمز SSH |
| systemd timers | پشتیبان شبانه، کنترل انقضای دارو، پیامک‌های یادآوری، تلاش مجدد رویدادها و کنترل مغایرت مالی |
| unattended-upgrades | نصب خودکار به‌روزرسانی‌های امنیتی سیستم‌عامل |

ساختار پوشه‌ها روی سرور:

```
/srv/724/app            کد برنامه (git) و فایل تنظیمات .env
/srv/724/venv           محیط پایتون
/srv/724/static         فایل‌های ثابت (CSS)
/srv/724/media          تصاویر عمومی (پزشک، کالا)
/srv/724/private_media  مدارک اسکن‌شده بیماران؛ هرگز از وب سرو نمی‌شود
/var/backups/724        پشتیبان‌ها
/var/log/724            لاگ برنامه
```

## ۱. پیش‌نیازها

- سرور با **Ubuntu 24.04** یا 22.04 یا **Debian 12**، حداقل ۲ گیگابایت رم و ۲ هسته و ۴۰ گیگابایت دیسک.
- **سرور داخل ایران** باشد: داده‌های سلامت بیماران باید در داخل کشور نگهداری شود.
- دسترسی root یا کاربری با sudo.
- برای HTTPS واقعی: در پنل دامنه، رکورد **A** برای `724.co.ir` و `www.724.co.ir` را روی IP سرور بگذارید. اعمال آن ممکن است چند ساعت طول بکشد. درستی‌اش را با `ping 724.co.ir` بررسی کنید.

## ۲. ورود به سرور

در ویندوز، PowerShell را باز کنید (IP را با IP سرور خود عوض کنید):

```
ssh root@203.0.113.10
```

رمز سرور را فقط در همین پنجره وارد کنید و هیچ‌جا ننویسید.

## ۳. نصب

روی سرور:

```bash
apt-get update && apt-get install -y git
git clone https://github.com/abdollah1366/724.co.ir.git /tmp/724
sudo DOMAIN=724.co.ir EMAIL=you@example.com bash /tmp/724/deploy/install.sh
```

- `EMAIL` برای هشدارهای انقضای گواهی است (اختیاری).
- اگر دامنه هنوز به سرور وصل نیست، `DOMAIN` را ننویسید. سایت روی `https://IP-سرور` بالا می‌آید، ولی گواهی خودامضاست و مرورگر هشدار می‌دهد. **در این حالت فقط با داده نمونه کار کنید**، نه اطلاعات واقعی بیماران. بعد از وصل شدن دامنه، همان دستور را با `DOMAIN` دوباره اجرا کنید.
- اجرای دوباره اسکریپت امن است: رمزها، داده‌ها و فایل‌ها حفظ می‌شوند.

در پایان، آدرس سایت و **آدرس پنل مدیریت** چاپ می‌شود. آدرس پنل تصادفی است (مثل `/manage-3fa9c1d2e7/`) تا قابل حدس نباشد. آن را یادداشت کنید. بعداً هم با این دستور دیده می‌شود:

```bash
sudo grep DJANGO_ADMIN_URL /srv/724/app/.env
```

## ۴. ساخت حساب مدیر ارشد

```bash
sudo 724-manage createsuperuser
```

`724-manage` همان `python manage.py` است که با کاربر برنامه اجرا می‌شود. هر دستور مدیریتی را با آن اجرا کنید، مثلاً `sudo 724-manage seed_services --demo` برای داده نمونه (فقط برای آزمایش).

## ۵. تنظیمات

همه تنظیمات در `/srv/724/app/.env` است. رمزها را خود اسکریپت ساخته است. این فایل را با کسی به اشتراک نگذارید.

```bash
sudo nano /srv/724/app/.env
sudo systemctl restart 724-web
```

موارد مهمی که باید خودتان پر کنید:

| کلید | توضیح |
|---|---|
| `SITE_PHONE`، `SITE_ADDRESS` | تلفن و نشانی در پایین صفحات |
| `SMS_BACKEND`، `SMS_API_KEY`، `SMS_SENDER` | پیامک. تا `console` است، پیامک‌ها فقط در لاگ ثبت می‌شوند |
| `PAYMENT_GATEWAY` | درگاه پرداخت مشاوره آنلاین. پیش‌فرض `none`: پرداخت اینترنتی خاموش و ثبت دستی در پنل ([TELEMED.md](TELEMED.md)) |
| `LAB_NAME`، `LAB_LICENSE_NO`، `LAB_TECHNICAL_DIRECTOR`، ... | مشخصات آزمایشگاه روی برگه جواب |
| `CLINIC_NAME` | نام درمانگاه در پیامک و مانیتور صف |
| `DJANGO_HSTS_SECONDS` | ابتدا ۳۶۰۰ (یک ساعت). وقتی HTTPS دامنه چند روز درست کار کرد، آن را `31536000` (یک سال) کنید |

## ۶. به‌روزرسانی به نسخه جدید

هر وقت تغییری در شاخه `main` ادغام شد:

```bash
sudo bash /srv/724/app/deploy/update.sh
```

این دستور ابتدا پشتیبان می‌گیرد، سپس کد، بسته‌ها و پایگاه داده را به‌روز و سرویس را دوباره راه‌اندازی می‌کند. شناسه نسخه قبلی را هم چاپ می‌کند.

**بازگشت به نسخه قبلی** (اگر نسخه جدید مشکل داشت):

```bash
sudo git -C /srv/724/app checkout <شناسه-نسخه-قبلی>
sudo systemctl restart 724-web
```

اگر نسخه جدید جدول‌های پایگاه داده را تغییر داده بود، پشتیبانی را که update.sh پیش از تغییر گرفت برگردانید (بخش ۷).

## ۷. پشتیبان‌گیری

- هر شب ساعت ۲:۳۰ به وقت تهران، از پایگاه داده و پوشه مدارک بیماران پشتیبان فشرده گرفته می‌شود. صحت فایل بررسی و کد SHA-256 کنارش ذخیره می‌شود. نسخه‌های قدیمی‌تر از ۳۰ روز حذف می‌شوند.
- پشتیبان دستی: `sudo systemctl start 724-task@backup` یا `sudo 724-manage backup_db`
- فهرست پشتیبان‌ها: `sudo ls -lh /var/backups/724`
- وضعیت آخرین پشتیبان: `sudo journalctl -u 724-task@backup -n 20`

**پشتیبان باید بیرون از سرور هم نگهداری شود.** اگر سرور از دست برود، پشتیبان روی خود سرور هم از دست می‌رود. دست‌کم هفته‌ای یک‌بار، از ویندوز در PowerShell:

```
scp -r root@203.0.113.10:/var/backups/724 D:\backup-724
```

این فایل‌ها اطلاعات پزشکی بیماران را دارند. آن‌ها را فقط روی دیسک رمزگذاری‌شده (مثلاً BitLocker) نگه دارید.

**بازگرداندن پشتیبان:**

```bash
sudo systemctl stop 724-web
cd /tmp
sudo cat /var/backups/724/db-YYYYMMDD-HHMMSS.dump | sudo -u postgres pg_restore --clean --if-exists -d app724
# مدارک بیماران (اگر فایل files-... وجود دارد):
sudo -u app724 python3 -m zipfile -e /var/backups/724/files-YYYYMMDD-HHMMSS.zip /srv/724/private_media/
sudo systemctl start 724-web
```

بازگرداندن را هر چند ماه یک‌بار روی یک سرور آزمایشی تمرین کنید تا مطمئن شوید پشتیبان‌ها سالم‌اند.

## ۸. کارهای زمان‌بندی‌شده

| زمان (تهران) | کار | سرویس |
|---|---|---|
| ۰۰:۳۰ | منقضی کردن سری‌های تاریخ‌گذشته دارو، پاک کردن نشست‌های قدیمی | `724-task@nightly` |
| ۰۲:۳۰ | پشتیبان | `724-task@backup` |
| ۱۰:۰۰ | پیامک یادآوری ویزیت، دارو و نوبت آزمایشگاه | `724-task@reminders` |
| هر ۱۰ دقیقه | مشاوره آنلاین: انقضای پرداخت‌نشده و بی‌پاسخ، بستن گفتگوی راکد، یادآوری ویزیت تلفنی/تصویری | `724-task@telemed` |

فهرست و زمان اجرای بعدی: `systemctl list-timers '724*'`

## ۹. امنیت

اسکریپت این موارد را انجام می‌دهد: حالت DEBUG خاموش، رمزهای تصادفی قوی، HTTPS اجباری و کوکی‌های امن، دیوار آتش، fail2ban، به‌روزرسانی امنیتی خودکار، اجرای برنامه با کاربر بدون دسترسی root و محدودیت نوشتن فقط در پوشه‌های لازم، پایگاه داده بسته به بیرون، و آدرس تصادفی پنل مدیریت.

کارهایی که خودتان باید انجام دهید:

1. **ورود SSH با کلید و خاموش کردن ورود با رمز.** در ویندوز: `ssh-keygen` و سپس محتوای `C:\Users\<نام>\.ssh\id_ed25519.pub` را در `/root/.ssh/authorized_keys` سرور بگذارید. وقتی ورود با کلید کار کرد، در `/etc/ssh/sshd_config` بنویسید `PasswordAuthentication no` و `sudo systemctl restart ssh`.
2. برای همه کارکنان رمز قوی و جدا بسازید و حساب مشترک ندهید. گزارش تغییرات هر کاربر ثبت می‌شود.
3. اگر از CDN (مثل ابرآروان) جلوی سایت استفاده کنید، IP واقعی بازدیدکننده‌ها به برنامه نمی‌رسد و تنظیم Nginx باید تغییر کند. پیش از فعال کردن CDN خبر دهید.
4. پشتیبان بیرون از سرور (بخش ۷).

اگر SSH سرور روی درگاه غیرعادی است و نگرانید اتصال قطع شود، اسکریپت را با `SKIP_FIREWALL=yes` اجرا کنید و دیوار آتش را دستی تنظیم کنید. اسکریپت درگاه SSH فعلی را خودش تشخیص می‌دهد و باز نگه می‌دارد.

## ۱۰. عیب‌یابی

| مشکل | دستور |
|---|---|
| وضعیت برنامه | `sudo systemctl status 724-web` |
| خطاهای برنامه | `sudo journalctl -u 724-web -n 100` یا `sudo tail -100 /var/log/724/724.log` |
| خطاهای Nginx | `sudo tail -50 /var/log/nginx/724-error.log` |
| خطای 400 (Bad Request) | آدرسی که باز کرده‌اید در `DJANGO_ALLOWED_HOSTS` در `.env` نیست |
| خطای 502 | برنامه بالا نیست؛ لاگ `724-web` را ببینید |
| گواهی صادر نشد | رکورد A دامنه را بررسی کنید و اسکریپت نصب را دوباره با `DOMAIN` اجرا کنید |
| بررسی تنظیمات امنیتی Django | `sudo 724-manage check --deploy` |
| وضعیت دیوار آتش | `sudo ufw status` |
