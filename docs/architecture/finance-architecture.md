# معماری ماژول مالی

این سند معماری بخش مالی سامانه ۷۲۴ را پس از پیاده‌سازی توضیح می‌دهد. وضعیت پیش از کار در [system-audit.md](system-audit.md) آمده است.

## ۱. قبل و بعد

| موضوع | قبل | بعد |
|---|---|---|
| ساختار | monolith ماژولار Django؛ حسابداری فقط برای داروخانه و آزمایشگاه | همان monolith؛ اپ تازه `apps/finance` به‌عنوان bounded context مالی، روی `apps/accounting` |
| ارتباط ماژول‌ها | فراخوانی مستقیم تابع | رویداد داخلی با transactional outbox (`apps/core/events.py`)؛ مالی به مدل‌های درمانی کلید خارجی ندارد |
| درآمد درمانگاه، توانبخشی و مشاوره آنلاین | ثبت مالی نداشت | صورتحساب، دریافت، علی‌الحساب و استرداد با سند حسابداری |
| دفتر کل | سند خودکار از اسناد داروخانه و آزمایشگاه | به‌علاوه دوره مالی، مرکز هزینه/درآمد، سند دستی، بستن سال، مغایرت‌گیری بانک |
| قرارداد و تسویه پزشک | نبود | قرارداد نسخه‌دار با تأیید، تسویه ماهانه قطعی با تأیید دومرحله‌ای |
| حقوق | نبود | اقلام قابل تنظیم، وام، محاسبه، تأیید و سند تعهد |
| روشن/خاموش کردن | نبود | feature flag سلسله‌مراتبی (`apps/core/flags.py`) |
| پایش | لاگ | به‌علاوه شناسه همبستگی، health check، صف رویداد، کنترل مغایرت روزانه |

چرا microservice نشد: سامانه روی هاست اشتراکی cPanel (MariaDB، Python 3.9، بدون Celery و Redis) اجرا می‌شود. جدا کردن سرویس‌ها روی این زیرساخت ممکن نبود و ریسک عملیاتی می‌ساخت. در عوض مرزها طوری کشیده شده‌اند که جدا کردن بعدی ممکن باشد:

- مالی فقط از `apps/finance/adapters.py` داده ماژول‌های دیگر را می‌خواند (فقط شناسه، نام و شماره پرونده). با جدا شدن سرویس، فقط همین فایل با فراخوانی API جایگزین می‌شود.
- ماژول‌های تولیدکننده (پرونده سلامت، مشاوره آنلاین، داروخانه، آزمایشگاه) هیچ import ای از مالی ندارند؛ فقط `events.publish` را صدا می‌زنند.
- صف outbox در جدول `core_outboxevent` است و می‌تواند بعداً به broker پیام منتقل شود.

## ۲. اجزا

```
apps/core/events.py        گذرگاه رویداد (publish، subscribe، dispatch، retry، health)
apps/core/flags.py         قابلیت‌های قابل روشن/خاموش
apps/core/middleware.py    RequestIDMiddleware (شناسه همبستگی X-Request-ID)
apps/accounting/           دفتر کل، دوره، مرکز هزینه، سند دستی، مغایرت بانک
apps/finance/
  models/billing.py        Invoice، InvoiceLine، Receipt، ReceiptTender، PaymentAllocation، Refund
  models/contracts.py      Contract، ContractVersion، ContractRule، ProviderSettlement، SettlementLine
  models/payroll.py        PayItemType، TaxBracket، PayrollProfile، ProfilePayItem، EmployeeLoan، PayrollRun، PayrollLine، PayrollItem
  services/                billing، contracts، settlements، payroll (همه قواعد کسب‌وکار اینجاست)
  integration.py           مصرف‌کننده رویدادهای ماژول‌های دیگر
  adapters.py              خواندن فقط‌خواندنی از ماژول‌های دیگر
  reconcile.py             کنترل‌های مغایرت
  views.py، api.py         صفحات و API نسخه ۱
  admin.py                 پنل مدیریت با دکمه‌های عملیات
  demo.py                  گردش نمونه با داده ساختگی
```

## ۳. جریان‌های اصلی

**ویزیت درمانگاه:** پزشک ویزیت را امضا می‌کند ← `ehr.encounter.signed` در همان تراکنش ذخیره می‌شود ← پس از commit، مالی صورتحساب پیش‌نویس می‌سازد (یا نهایی، طبق `FINANCE_RULES`) ← صندوق‌دار صورتحساب را ثبت و وجه را دریافت می‌کند. اگر برای همان نوبت در پذیرش صورتحساب صادر شده باشد، صورتحساب دوم ساخته نمی‌شود.

**مشاوره آنلاین:** پرداخت ← `telemed.payment.paid` ← صورتحساب نهایی و دریافت. مشاوره انجام‌نشده ← `refund_due` ← ابطال صورتحساب (بستانکاری بیمار). استرداد در ماژول مشاوره ← `refunded` ← سند استرداد.

**داروخانه و آزمایشگاه:** ثبت حسابداری عمداً همان ثبت هم‌زمان داخل تراکنش خود سند می‌ماند تا کاردکس همیشه با دفتر کل برابر باشد. رویداد `.posted/.reversed` فقط سند حسابداری موجود را پیدا و به رویداد پیوند می‌دهد؛ هیچ سند تازه‌ای ساخته نمی‌شود.

**تسویه پزشک:** حسابدار تسویه ماه را می‌سازد ← محاسبه قطعی از صورتحساب‌ها، تخصیص‌ها و استردادها با ثبت جزئیات هر ردیف ← تأیید مالی ← تأیید مدیریتی (نفر سوم) ← ثبت سند (بدهکار هزینه حق‌الزحمه به تفکیک مرکز، بستانکار بدهی به پزشک).

**حقوق:** منابع انسانی لیست ماه را می‌سازد ← محاسبه از اقلام فعال ← تأیید مدیر مالی ← ثبت سند تعهد.

## ۴. تصمیم‌های کلیدی

1. پول همیشه ریال صحیح (`PositiveBigIntegerField`/`BigIntegerField`)، درصد با `Decimal`، گرد کردن نیم به بالا، تقسیم به روش بزرگ‌ترین باقی‌مانده (`apps/finance/money.py`). هیچ float در محاسبه مالی نیست. ارز صریح: `FINANCE_CURRENCY = "IRR"` و فیلد `currency` در API.
2. اسناد نهایی حذف یا ویرایش نمی‌شوند؛ اصلاح فقط با سند برگشت (`PostedDocument`). آرتیکل‌های دفتر (`ImmutableRecord`) قابل حذف نیستند.
3. محدودیت‌های پایگاه داده سازگار با MariaDB: یکتایی شرطی با `apps/core/fields.unique_when` (ستون GeneratedField) به‌جای `UniqueConstraint(condition=...)`؛ CheckConstraint فقط مقایسه ساده.
4. هر handler رویداد idempotent است: یکتایی منبع صورتحساب، کلید idempotency دریافت و استرداد، کلید یکتای ردیف تسویه.
5. خاموش کردن قابلیت هیچ داده‌ای را حذف نمی‌کند؛ رویدادها «در انتظار» می‌مانند و با روشن شدن دوباره پردازش می‌شوند.
6. هیچ نرخ قانونی (بیمه، مالیات، ضریب اضافه‌کاری) در کد نیست.
7. تأیید کاربر در قرارداد «تأیید» است، نه امضای الکترونیکی؛ این در متن گزارش تغییرات هم نوشته می‌شود.
