# آزمون و استقرار ماژول مالی

## اجرای محلی

```bash
pip install -r requirements.txt
export DJANGO_DEBUG=true            # در توسعه؛ بدون آن DJANGO_SECRET_KEY لازم است
python manage.py migrate            # پایگاه داده SQLite محلی؛ نقش‌ها هم ساخته می‌شوند
python manage.py finance_demo --password '<رمز دلخواه>'   # فقط روی پایگاه داده آزمایشی
python manage.py runserver
```

`finance_demo` کاربران نمونه (`demo_fin_cashier`، `demo_fin_accountant`، `demo_fin_manager`، `demo_fin_approver`، `demo_fin_hr`، `demo_fin_employee`) و یک گردش کامل با داده ساختگی می‌سازد و در پایان کنترل‌های مغایرت را اجرا می‌کند. هرگز آن را روی پایگاه داده واقعی اجرا نکنید.

صفحات: `/finance/` (داشبورد)، `/finance/cashier/`، `/finance/invoices/`، `/finance/receivables/`، `/finance/reports/...`، `/finance/integration/`، `/finance/settings/`؛ قرارداد، تسویه، حقوق، دوره مالی، سند دستی و مغایرت بانک در پنل مدیریت (`/admin/finance/` و `/admin/accounting/`).

## آزمون‌ها

```bash

python manage.py test apps.finance apps.core.tests.test_events
POSTGRES_DB=... POSTGRES_USER=... POSTGRES_PASSWORD=... python manage.py test   # PostgreSQL
MYSQL_DATABASE=... MYSQL_USER=... MYSQL_PASSWORD=... python manage.py test     # MariaDB (مثل هاست)
```

## استقرار روی staging

1. نسخه پشتیبان پایگاه داده staging: `bash deploy/tasks.sh backup` (یا روی cPanel از بخش Backup).
2. کد را به‌روز کنید (`deploy/update.sh` روی VPS یا Git Version Control در cPanel).
3. `python manage.py migrate` — همه migrationها افزایشی‌اند (جدول و ستون تازه و داده پایه با get_or_create). هیچ جدول یا ستونی حذف یا بازنویسی نمی‌شود.
4. `python manage.py check --deploy`.
5. `python manage.py finance_reconcile` باید بدون خطا باشد.
6. دوره مالی سال جاری را در پنل (`حسابداری > دوره‌های مالی`) تعریف کنید.
7. اقلام قانونی حقوق: نرخ معتبر و جدول مالیات سال را وارد و سپس فعال کنید.
8. نقش‌ها را به کاربران بدهید (صفحه کارکنان).
9. Cron ها را اضافه کنید (`docs/HOSTING.md` بخش ۴): `tasks.sh events` هر ۵ دقیقه و `tasks.sh finance` روزانه. روی VPS تایمرهای `724-events.timer` و `724-finance.timer` با `update.sh` فعال می‌شوند.
10. با کاربران نمونه staging یک گردش کامل را دستی امتحان کنید.

## استقرار روی production (cPanel، MariaDB)

این مراحل باید توسط مسئول هاست و با تأیید انسانی انجام شود؛ در این کار روی production هیچ تغییری داده نشده است.

1. **پیش از هر چیز پشتیبان کامل** پایگاه داده و پوشه media بگیرید و از قابل بازیابی بودن آن مطمئن شوید.
2. برای راه‌اندازی تدریجی، قابلیت‌ها را پیش از migrate خاموش کنید (در `.env`):
   `FEATURE_FLAGS_OFF=finance.integration.clinic,finance.integration.rehab,finance.payroll`
   با این کار رویدادها ذخیره می‌شوند ولی پردازش نمی‌شوند و بعداً با روشن کردن قابلیت پردازش خواهند شد.
3. کد را به‌روز و `migrate` را اجرا کنید؛ Passenger را راه‌اندازی دوباره کنید.
4. `python manage.py finance_reconcile` و صفحه `/finance/health/` را بررسی کنید.
5. دوره مالی، نقش‌ها و Cron ها را مثل staging تنظیم کنید.
6. قابلیت‌ها را یکی‌یکی از صفحه «تنظیمات ماژول‌ها» (با نوشتن علت) روشن کنید و صفحه «وضعیت اتصال‌ها» را زیر نظر بگیرید.

## روشن و خاموش کردن ماژول‌ها

- صفحه `/finance/settings/` (مجوز `core.change_featureflag`): هر تغییر علت می‌خواهد و در گزارش تغییرات ثبت می‌شود. `finance.accounting` حیاتی است و از اینجا خاموش نمی‌شود.
- یا با `.env`: `FEATURE_FLAGS_OFF=key1,key2` و `FEATURE_FLAGS_ON=...`. مقدار ذخیره‌شده در صفحه تنظیمات بر `.env` اولویت دارد.
- خاموش کردن والد (مثلاً `finance`) همه زیرمجموعه‌ها را خاموش می‌کند؛ `finance.settlements` به `finance.contracts` و `finance.billing` وابسته است.
- خاموش کردن هیچ داده‌ای را حذف نمی‌کند: صفحات و منوها پنهان می‌شوند، رویدادها در انتظار می‌مانند و ماژول‌های درمانی بدون تغییر کار می‌کنند.

## بازگشت (rollback)

- **بی‌خطرترین راه:** خاموش کردن قابلیت‌ها. داده‌ها می‌مانند و ماژول‌های دیگر وابسته نیستند.
- **بازگشت کد:** نسخه قبلی کد را مستقر کنید. جدول‌های تازه بدون استفاده می‌مانند و به کد قدیمی آسیب نمی‌زنند، چون فقط جدول و ستون nullable اضافه شده است (ستون‌های تازه `accounting_journalline.cost_center_id` و `accounting_account.bank_name/account_no` با کد قدیمی سازگارند).
- **بازگشت migration** (`migrate finance zero`، `migrate core 0002`، `migrate accounting 0003`) داده مالی ثبت‌شده را حذف می‌کند و فقط با پشتیبان و تأیید مسئول مالی مجاز است. migrationهای داده (`accounting 0005`، `finance 0002`) بازگشت بی‌اثر دارند و چیزی حذف نمی‌کنند.
